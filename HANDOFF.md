## What it is

Maritime disruption monitoring. Ingests IMF PortWatch, GDACS, 5 maritime RSS feeds, GDELT raw
files and Google News; clusters reports into events; matches events to shipments by
port/chokepoint; prices the options (wait / reroute / invoke force majeure) from each Bill of
Lading's contract terms; asks an LLM for a cited recommendation; drafts the force majeure
notice and customer email; shows it all on a dashboard for human approval.

## Architecture (changed substantially — the README predates this)

It was a single Streamlit app. It is now **React + FastAPI, deployed publicly**, with the
Streamlit app kept as a legacy/local tool.

## LLM setup

- **Local dev:** Ollama, `NEMOTRON_MODEL=majeure-nemotron` (16k ctx, `ollama/Modelfile`).
- **Deployed:** NVIDIA hosted API (`nvidia/nemotron-3.5-lightning-30b-a3b`). It's a *thinking*
  model with highly variable latency — a trivial prompt returns in ~1s, a real analytical one
  can exceed 60s even with `reasoning_effort=none`.
- **Gemini is the fallback** (`gemini-3.6-flash`) and in practice does most of the answering.
  `/api/ask` gives Nemotron a **20s** budget (overriding `NEMOTRON_TIMEOUT`'s 300s default,
  which otherwise blocked the fallback for 5 minutes) then falls through. Response includes
  `"via": "gemini-fallback"` when it does.
- Keys live in `.env` locally and in Render's Environment tab for the deploy.

## Live data refresh on the deployed site

Render's free tier has **no persistent disk and no scheduler**. An external cron (cron-job.org,
every 15 min) POSTs to:

```
https://majeure-api.onrender.com/api/pipeline/run?token=<PIPELINE_TRIGGER_TOKEN>
```

Two gotchas that cost time: it must be **POST** (a browser GET returns 405), and the token is
base64 so `+` and `=` **must be URL-encoded** (`%2B`, `%3D`) or it silently 403s. The token is
auto-generated by Render — read it from the service's Environment tab.

Hitting this also keeps the free instance from idling out. **A code redeploy always resets
`data/majeure.db` to the committed snapshot**, regardless of pipeline runs in between.

## Database backends

`src/store.py` is the one seam. `DB_BACKEND=sqlite` (default) uses `data/majeure.db`;
`DB_BACKEND=postgres` uses `DATABASE_URL` (Supabase). It returns a connection that behaves like a
`sqlite3.Connection` for everything this codebase does, and translates the SQL on the way through,
so call sites did not have to branch.

Run `python src/migrate_to_postgres.py` to copy SQLite -> Postgres and diff every table's row
count; `--dry-run` reports without writing, `--verify-only` just diffs.

`data/majeure.db` is **no longer committed**. Postgres is the deployed source of truth, so the
old trick of committing a snapshot (and the 2.3 MB of binary churn on every push) is gone. A fresh
clone has no database until you either point `DATABASE_URL` at Supabase or run the pipeline once
locally to build a SQLite one.

Because of that, never guard on `db_path.exists()` -- use `store.database_ready(db)`. The file is
genuinely absent on the deployed service, and a bare `.exists()` check would refuse to run against
a perfectly healthy Supabase instance. Eight such guards existed and all had to be converted; the
one in the API's `_connect()` would have answered 503 to every request.

Things that will bite you here:

* **Use Supabase's Session pooler string.** The direct `db.<ref>.supabase.co` host is IPv6-only and
  Render has no IPv6 egress; the transaction pooler on `:6543` cannot hold prepared statements,
  which psycopg uses by default.
* **Percent-encode the password.** `@` in a password makes the URL parse the host wrongly and you
  get "failed to resolve host", which reads like DNS. `@` -> `%40`.
* **The publishable/secret API keys are not this.** They are for PostgREST; the pipeline needs SQL.
* **Postgres rejects SQL that SQLite waves through.** A bare column beside `MAX()` without a
  `GROUP BY` entry, `SUM(boolean)`, and `round(double, int)` all work in SQLite and all fail in
  Postgres. Four of `faq.py`'s thirty answerers had to be rewritten; run them against both
  backends after touching any aggregate.
* **`store.PRIMARY_KEY` must match real unique constraints.** `ON CONFLICT` needs one, and a wrong
  entry only fails at write time. `store.check_primary_keys(conn)` asks Postgres itself.

## Traps worth knowing (each of these cost real debugging time)

1. **`init_db.py` was once ported to Snowflake and never reverted**, which silently broke the
   pipeline's DB step for an hour — fetches succeeded, nothing reached the database. If data
   looks frozen, check `data/pipeline.log` for `Database FAIL`.
2. **Snowflake is parked, not used.** `src/db.py` + `docs/SNOWFLAKE_SCHEMA.sql` exist and are
   complete but wired to nothing. SQLite is the live path.
3. **MapLibre's worker needs two files.** `maplibre-gl-worker.mjs` is imported via `?url` in
   `RiskMap.tsx`, and its sibling `maplibre-gl-shared.mjs` is copied to `public/assets/` by a
   `postinstall` script. Miss either and the map renders blank *with no console error* — the
   failure happens inside the worker thread. Check rendered canvas pixels, not error logs.
4. **Locale-dependent formatting.** `toLocaleString()`/`strftime("%b")` follow the viewer's
   locale ($32 500 vs $32,500; French month names). Use `fmtMoney`/`fmtDate` in `api.ts`.
5. **Ship positions are estimates, not AIS.** Computed from elapsed ETD→ETA along the
   `searoute` path. No ingested source carries vessel positions. The UI says so explicitly —
   keep it that way.
6. **Routes must use `src/routing.py`.** Straight port-to-port lines visibly cut across land.
   Both the Streamlit map and the API share that module deliberately.
7. **Sidebar freshness has two different clocks**: `last_fetched_min` (did the pipeline run) vs
   `last_ingested` (age of a source's newest article). A quiet trade feed is polled every 5 min but
   may not have published for days. Don't conflate them. Fetch times now live in the **`pipeline_state`
   table**, not just `data/pipeline_state.json` — that file is gitignored and Render's free tier has
   no persistent disk, so the deployed API could never read it and every "Fetched" cell rendered as
   a dash. `run_pipeline.py` writes both; the API reads the table and falls back to the file.
8. **`backend/requirements.txt` must carry the INGEST deps, not just the API's.** Render builds with
   `rootDir: backend` and never installs the repo-root `requirements.txt`, but
   `POST /api/pipeline/run` shells out to `run_pipeline.py` in that same container. `feedparser` was
   missing, so `parse_rss.py`, `fetch_google_news.py` and `fetch_official.py` died on import while
   the run still logged "ok" — and the site served the committed DB snapshot indefinitely.
9. **The FAQ router answers before the model does.** `src/faq.py` holds 194 hardcoded questions over
   30 topics and answers them from SQL in ~1 ms. The *questions* are hardcoded; every *answer* is
   computed from the live database, so a routed answer is never staler than a generated one. Run
   `python src/faq.py --selftest` after touching it: entries silently steal each other's questions
   otherwise. Anything it isn't confident about falls through to Nemotron/Gemini untouched.

### Added since the last handoff

* **25 ingest sources, up from 9.** 17 trade-press RSS feeds (`parse_rss.py`) plus four first-party
  government publishers in the new `src/fetch_official.py`: NOAA NHC, JTWC, USGS quakes and NGA
  NAVAREA warnings. Three general-logistics feeds are `STRICT`-filtered through `is_maritime()`.
* **Source credibility tiering.** `PUBLISHER_TIER` in `common.py` grades every source 1-4, and
  `cluster_events.py` starts an event's confidence from its best source instead of a flat 0.35.
  Single-publisher events now span 0.35-0.95 by who reported them rather than all scoring alike.
* **A real fleet.** `src/fleet.py` builds the shipment book on 10 real container ships with
  IMO-check-digit-validated numbers across 5 real carriers (Maersk, MSC, CMA CGM, COSCO, Evergreen),
  sourced from Wikidata. Vessel identity and carrier are real; **contract terms remain synthetic**
  and every row carries `vessel_source` / `carrier_source` / `terms_source` so the UI says which is
  which. Positions are still schedule estimates — that invariant did not change.
* **Ask Majeure latency: ~39 s → ~1 ms** for common questions, via the `faq.py` router above.
* **Citations actually work.** The system prompt no longer makes the model emit a literal `[n]`,
  the context carries 6 sources per decision instead of 3, and `ChatWidget` renders markdown so
  links are clickable rather than printed as raw `[1](https://…)`.

## Known gaps

* **No AIS.** Vessel positions remain estimated. `aisstream.io` (free key, WebSocket) is the path to
  real positions; nothing here claims live tracking and nothing should until that exists.
* **Carrier attribution is by vessel-name prefix**, not a registry lookup. Equasis and IMO GISIS both
  need credentials and neither publishes an API; the registered owner of a chartered ship is often a
  leasing company rather than the operating line anyway.
* **UKMTO and MARAD MSCI are 403 from a server** — the two most authoritative sources for exactly the
  Hormuz/Bab el-Mandeb events this product cares most about. Worth a headless fetch.
* **The model path is still slow** for genuinely novel questions (~20-40 s). The documented "20 s
  Nemotron budget then fall back to Gemini" does *not* bound it: `requests`' timeout is a per-read
  gap, not a total deadline, so a model trickling tokens resets the clock indefinitely. Measured 39 s
  responses that never triggered the fallback. Putting Gemini first for chat would fix it, but that
  flips the primary model and is a product call, not a code cleanup.
